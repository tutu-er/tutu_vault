# PowerAtlas: Towards Electricity-Computing Co-Scheduling for Power Systems

- **论文信息**: Kaiwen Jiang et al., arXiv:2607.26710, 2026年7月
- **链接**: https://arxiv.org/abs/2607.26710
- **代码**: https://github.com/JAVA-Jiang/PowerAtlas

---

## 1. 解决了什么问题

AI数据中心的快速增长带来了一个两难问题：计算任务有SLA（服务等级协议）约束，电网有物理安全约束，这两个世界的调度从来是各管各的。直接用大模型做调度？出来的方案往往物理上不可行——线路过载、负荷失配。PowerAtlas提供了一个能让LLM Agent输出**既满足SLA又满足电网约束**的联合调度方案的框架。

## 2. 核心方法解读

想象你是电网调度员，突然被告知还要管数据中心的任务排期。你拿起一个GPT问"帮我排一下"，结果它给的方案很好看，但一跑潮流计算——三条线路过载。

PowerAtlas的做法很聪明：**不让LLM做它不擅长的事**。

它把LLM当作"高级调度参谋"而不是"数值计算器"。核心设计理念是：
- LLM负责理解任务语义、分析历史模式、生成调度建议
- 物理约束验证交给专业的潮流计算模块
- 两者之间通过"约束反馈循环"迭代交互——LLM出方案→物理模块验证→把违例信息返回给LLM→修正方案→再验证...

就像一个有经验的调度员拿着计算器工作：直觉出方案，算一下行不行，不行就调，直到可行。

## 3. 算法/模型框架

```
┌─────────────────────────────────────────────┐
│                PowerAtlas 框架                │
├─────────────────────────────────────────────┤
│  ┌─────────┐    ┌──────────┐    ┌─────────┐ │
│  │ LLM Agent│───▶│ 约束验证  │───▶│ 决策输出 │ │
│  │ (调度参谋) │◀───│ (潮流计算) │    │ (可行解) │ │
│  └─────────┘    └──────────┘    └─────────┘ │
│       │              │              │        │
│  历史实例库      电网物理约束      SLA满足    │
│  领域知识        线路容量        任务完成    │
└─────────────────────────────────────────────┘
```

**关键组件：**

1. **LLM Agent层**：接收计算任务请求 + 电网拓扑/负荷信息，生成初步调度
2. **物理验证层**：运行AC/DC潮流计算，检测线路过载、电压越限
3. **约束反馈机制**：将违例信息以自然语言形式反馈给LLM，触发修正
4. **ECBench基准**：从真实省级电网+数据中心数据构建的2000个调度实例，每个都有oracle最优解

**实验亮点：**
- 与某省电力公司合作，构建真实电力-计算联合网络
- 11个LLM上测试，3个开源模型取得consistent feasibility and cost gains
- 开源代码和基准数据集

## 4. 关键创新点

1. **"LLM + 求解器"的接地气用法的系统化实现**：不是让LLM替代优化器，而是让它做"逻辑推理+方案生成"，验证交给专业工具
2. **ECBench**：第一个电力-计算联合调度的标准化基准，2000个实例带最优解
3. **真实工业数据验证**：与省级电网合作，不是simulation only
4. **约束反馈循环**：LLM能从错误中学习修正，不是一次性输出

## 5. 与已有方法的区别

| 维度 | 纯LLM调度 | 纯数学优化 | PowerAtlas |
|------|----------|-----------|------------|
| 物理可行性 | ❌ 无法保证 | ✅ 严格保证 | ✅ 通过验证保证 |
| 灵活性 | ✅ 语义理解强 | ❌ 固定模型 | ✅ 兼具二者 |
| 计算效率 | 中等 | 大型MILP很慢 | 中等（迭代） |
| 可解释性 | 高 | 低 | 高（LLM输出可读） |

## 6. 为什么值得关注

这个工作的方向非常对——**不是用LLM替代数学模型，而是用LLM包装数学模型**。对于电力市场/优化研究者来说，这意味着可以把已有的UC/OPF求解器作为工具注册到LLM Agent中，让LLM处理市场规则理解、异常情况推理等"软"问题，让求解器处理"硬"约束。这就是"Agent + Solver"的研究范式。

## 7. 待思考的问题

- 约束反馈循环的收敛性有理论保证吗？会不会陷入无限循环？
- 在实时市场的5分钟调度窗口内，LLM推理延迟是否可行（一次推理可能数百ms到数秒）？
- 能否扩展到含随机性的场景（新能源不确定性+计算任务不确定性）？
- ECBench是否包含了不同类型的数据中心负载（训练 vs 推理 vs 微调）？
