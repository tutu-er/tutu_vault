## 1. 解决了什么问题

LLM Agent 在工业（尤其电力系统）场景的自动化分析很有前景，但严格评测一直卡在"真实运维数据保密、公开资源又无法刻画证据之间的链式依赖与异构性"。本文要解决的是：**如何造一个可控、可复现、能考察"自主检索 + 推理"能力的电力系统 Agent 评测基准**。

## 2. 核心方法解读（师兄视角）

核心思路是"用一条公共的依赖链把不同类的异构数据串起来"。打个比方：电网里某条线路的告警，不是孤立的——它背后对应着某个设备的遥测异常，遥测异常又对应着一份运维工单，工单再对应某条调度指令……以前的做法是每类数据单独生成，互相之间对不上号，Agent 就算答对也是靠"碰"，测不出它到底会不会顺着链条查证据。PowerBench 反过来：**先生成一条完整的因果/依赖链，再沿着这条链去生成遥测、文档、设备台账等各类数据**，保证它们之间真的有可追溯的关联。这样出的 300 道题，就必须真的"找到证据 → 读懂证据 → 用工具 → 推理 → 交答案"才能做对。

## 3. 算法/模型框架说明

- **数据生成框架**：以"公共依赖链（dependency chain）"为核心，派生出 100 类设备、761 台设备、两年 1335 万条小时级遥测记录、24939 份运维文档。
- **评测任务**：三大任务族，共 300 题，覆盖"证据发现、内容检索、工具调用、证据推理、答案提交"全链路。
- **约束条件**：限制工具调用次数与时间预算，贴近真实工业部署。
- **指标**：joint accuracy（联合准确率），以及按环节拆分的 trace 分析（证据发现/检索/工具/推理/提交各自的得分）。

## 4. 关键创新点

1. **依赖链驱动生成**：不是"先有数据再出题"，而是"先有事实链再反推数据"，从根上保证题目可验证、无信息泄漏。
2. **全链路 trace 拆解**：不只看最终对不对，还能量化 Agent 到底卡在哪个环节（找不到证据 vs 找到了读不懂 vs 工具用错）。
3. **受限工具+时间预算**：把"真实工业里 Agent 不能无限调用工具"这个现实约束显式建模进评测。

## 5. 与已有方法的区别

已有的电力领域 LLM/Agent 评测（比如 RestoreBench 这类）往往只覆盖单一任务（如潮流计算、故障恢复），数据也偏合成、异构关联弱。PowerBench 强调"跨类型异构数据 + 链式依赖 + 受限资源"，考察的是 Agent 的**自主检索与多步推理**，而不只是单点问答或代码生成。与通用 Agent 基准（如 SWE-bench、GAIA）相比，它把领域数据保密、异构、链式依赖这些电力系统特有的痛点也纳入进来了。

## 6. 为什么值得关注

如果我们要做"电力系统 LLM Agent"方向，这个基准是现成的**评测抓手**：能定量说明我们 Agent 的检索/推理能力到底强在哪、弱在哪，也能作为方法对比的公共标尺。best model 也只有 74.2% joint accuracy，说明还有明确的研究空间，是很好的切入点。

## 7. 待思考的问题

- 依赖链的"真实性"如何保证？生成的文档会不会带有模板化的可被 LLM 利用的统计线索？
- joint accuracy 是否过度惩罚了"部分对"的答案？能不能引入 partial credit？
- 这个基准能不能反向指导 Agent 设计（比如"证据发现"弱就加强检索，而不是笼统地堆 prompt）？
- 对中文/国产模型的适配如何，数据与题目是否开源到可直接跑？（仓库 open-compass/PowerBench）
