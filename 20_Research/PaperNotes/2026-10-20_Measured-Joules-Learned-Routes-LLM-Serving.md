## 1. 解决了什么问题

LLM 和 agentic AI 的推理能耗随模型规模增大、推理轨迹变长而飙升；但实际中很多 query 根本用不到最大最强的模型，把它们全丢给大模型造成大量不必要的算力和能耗浪费。本文要解决：**如何在一个异构 LLM 池子里做"自适应路由"，在不明显损失任务性能的前提下降低推理能耗**。

## 2. 核心方法解读（像师兄讲给你听）

核心是一个"读 query、选模型"的路由器（router）。

第一步先做**离线画像**：搞一场 offline tournament，把候选模型逐个跑一遍，记录每个 query 在"正确率、延迟、功耗、GPU 能耗"四个维度上的表现。这样就有了真实的能耗测量（不是估计值），标题里的 "Measured Joules" 就是这个意思。

第二步训练路由器：先用**监督微调（SFT）**教它"什么样的 query 该选哪个模型"，再用 **GRPO（Group Relative Policy Optimization）** 做强化微调，目标是在"精度—能耗"的 trade-off 上寻优。GRPO 是现在很流行的 RLHF 替代方案，不需要单独的 critic 模型，用组内相对奖励来更新策略，省显存又稳定。

结果发现：学到的路由能根据 query 上下文"有选择地"分配大模型算力——难的问题给大模型，简单的问题给便宜的小模型。更妙的是，作者在七个 benchmark 任务上观察到一个**"精度—能耗"的尖锐相变（phase transition）**：路由器的行为在某个临界点附近剧烈切换，这给"在保持性能的同时压能耗"提供了很实用的工程直觉。

## 3. 算法/模型框架说明

1. **候选池 + 画像**：固定候选模型池，offline tournament 记录每个 query 的正确率/延迟/功耗/GPU 能耗。
2. **路由器训练**：SFT（监督微调，学"query → 模型"映射）→ GRPO（组相对策略优化，用测量到的能耗和精度构造奖励，做强化微调）。
3. **路由推理**：部署时路由器读 query，选中一个 answer model 执行。
4. **分析**：七个 benchmark 上画出精度—能耗的相变曲线，给出路由行为与能耗的定量关系。

## 4. 关键创新点

- **用真实测量（measured joules）而非估算**来做能耗感知的路由，把能耗当成一等的优化目标。
- **SFT + GRPO 两步训练**路由策略，把能耗/精度权衡直接编码进奖励。
- 发现**精度—能耗的相变现象**，为路由策略的"甜点区"提供了可操作的设计依据。

## 5. 与已有方法的区别

- 相比"所有 query 统一走最大模型"或"固定小模型"，本文是按 query 上下文自适应分配算力。
- 相比只用正确率做路由的 cascade/router 方法，本文把**实测 GPU 能耗**纳入训练目标，是 energy-aware 而非仅 accuracy-aware。
- 相比需要 critic 模型的传统 PPO，用 GRPO 更省资源、更稳。

## 6. 为什么值得关注

- 直接关联"大模型"和"能源"两个方向：AI 推理能耗正成为数据中心与电网负荷的重要变量，energy-aware routing 是"AI 自身能耗优化"的一个抓手。
- 思路可迁移到我关注的 **AI 数据中心与电网协同**：如果把"候选模型池"换成"不同电价/碳强度的推理节点"，路由决策就从"省能耗"变成"省电费/降碳"——本质是同一个"上下文相关资源分配"问题。
- GRPO + 实测能耗奖励的范式，可复用到其他资源受限的决策路由场景。

## 7. 待思考的问题

- 能耗测量是静态画像，实际部署中负载、硬件、温度都会漂移，如何做在线自适应路由？
- "精度—能耗相变"是否通用，还是只在特定 benchmark/模型池下成立？
- 能否把路由目标从"省能耗"扩展到"省电费/降碳/配合电网需求响应"，即 time/location-aware 的推理调度？
- GRPO 的奖励如何设计，才能在不牺牲安全关键任务精度的前提下压能耗？
